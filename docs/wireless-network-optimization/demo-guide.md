## 这是怎样的 Agentic Memory

这里的 memory 是业务处理经验：保留一张工单遇到什么、当时看见什么、选择什么、实际做了什么、结果如何，以及什么时候可以把结果用于下次决策。聊天记录仍由 SDK 保存，但不代替这些业务记忆。

Harness 负责根据用户目标选择 Skill 和工具。模型组织根因假设、证据解释与方案对照；工具实际计算统计、检索经验、运行 ECHO 候选排序和值选择、保存事实、比较效果和编译经验。分析无需每次完成工单全流程，完整闭环也不是固定回答模板。

有三段可独立使用的路径：

1. **数据分析**：读取场景 → 计算基线、时段、阈值与同群对照 → 解释支持与反对的根因线索。
2. **经验辅助决策**：编译并检索历史 → 正向候选与反证分池 → 源 ranker 排序 → 用当前快照适配目标值 → 说明验证与回退条件。
3. **反馈后学习**：冻结方案和依据版本 → 读取方案反馈 → 保存反馈中的执行字段 → 同口径效果评价 → 导出 Trace → 源编译器生成新版本 → 对照新旧候选、计数、评分与来源。

第三段只在用户要求完整处理、反馈评价或经验更新时推进。普通分析不会预读未来结果。数据截止时间可以推进到评价可见且满足七天成熟边界之后；这不表示系统真的在现实中等待了多天，也不构成论文完整时序回放。

每个场景的当前忙时快照与时序文件中同对象、同指标、同窗口的观测保持一致。执行后描述性评价与预置的长期评价标签分别保存，长期标签有独立来源与可见时间，不能由一次短期改善直接推定。再次处理可以复用同一输入快照，并按新的数据截止时间平移反馈窗口；它不会自动采集新观测。

## 浏览器里怎样使用

安装编译依赖后，运行根目录的 `./start.sh`，访问 `http://localhost:5173/chat`。侧栏点“场景库”，选择一个场景：

- **分析场景**：只做决策前分析，展示异常、历史支持、反证、根因假设和候选方案。
- **反馈与经验更新**：额外冻结候选，读取执行反馈，比较效果、生成新记忆版本，再复盘发生了哪些变化。

“能力中心”继续展示业务能力；聊天中的“执行过程”会显示实际工具阶段。成功调用工具、保存方案、执行成功、达到评价标准和生成经验版本是不同状态，不会合并称为“网优完成”。

## 建议的分析顺序

### 1. 商圈忙时拥塞低速率：从数据走到可比较的方案

选择“商圈忙时拥塞低速率”。先看用户平均吞吐、PRB、SINR 与同群小区。让助手说明基线和近期的差异、下降是否集中在忙时，以及链路质量是否支持“拥塞”假设。再比较两种有历史支持的候选与失败反证，明确当前值、目标值和约束来源。

可追问：

> 为什么不能只凭 PRB 高就确定根因？对照小区和 SINR 分别提供了什么证据？

> 这两个候选分别有多少有效评价？成功比例、样本量与可信度下界怎样影响排序？当前缺哪些验证数据？

> 冻结适用候选，继续读取方案反馈、效果评价和经验沉淀，再比较新旧版本。

### 2. 负荷与质量反证：历史有效也可能不适用于当前

选择“商圈忙时拥塞低速率 · 负荷与质量反证”。该场景保留高负荷，同时提供恶化的 SINR，不能直接套用普通容量场景结论。合成反馈中，负荷均衡候选存在反效果；用于展示模型是否注意当前反证，以及失败如何回到经验中。

> 当前有哪些证据反对“只调负荷均衡就能解决”？如果仍选择该候选，先冻结判断和保护指标，再读取方案反馈，保留失败结果学习。

新增失败可能降低某条经验的支持程度，但不保证必然改变排序或触发某个状态转换。要报告真实工具结果，不能预设“学习后一定更准”。

### 3. 高铁切换与跨时窗脏数据：先判断数据能否一起用

先选择“高铁沿线切换失败”，再选“高铁沿线切换失败 · 跨时窗脏数据”。后者故意加入一条来自另一时窗、数值看起来更好的观测，必须隔离，不能与当前窗口平均或用它排除异常。

> 哪条观测不可比，原因是什么？去掉它之后，还有哪些证据支持移动性问题，哪些检查能区分邻区、覆盖和目标侧资源？

### 4. 缺少当前参数：能给方向，不能编造目标值

选择“园区晚高峰接入失败 · 缺少当前参数”。历史经验与候选仍可比较，但当前参数值未知，值选择工具应返回缺口，不能抄历史 after 值或取范围中点。

> 先完成能做的历史与指标分析；哪些结论可以给，哪些必须等当前参数补齐？

### 5. 厂家不匹配：有知识不等于存在可迁移候选

选择“城郊弱覆盖投诉 · 厂家不匹配”。当前厂家与相应历史支持不同，应返回没有兼容候选，保留已有观测与一般排查方向，不创造当前厂家成功案例。

### 6. 其他现场问题

| 场景 | 重点展示 | 有价值的追问 |
| --- | --- | --- |
| 园区接入失败 | 接入阶段、重传、覆盖和设备告警的区分；参数语义与效果证据的区别 | “哪项数据能够区分接入资源不足与弱覆盖？” |
| 城郊弱覆盖 | RSRP、空间人群、对照小区；覆盖收益与干扰保护指标 | “优化覆盖时还要监测哪些退化风险？” |
| 工业园干扰 | 上行噪声与时段分布；外部、同频、设备与负荷线索 | “仅凭这些观测能定位干扰源吗？” |
| 校园视频卡顿 | 用户吞吐与视频 KQI；质量、负荷、覆盖和应用因素 | “视频卡顿是否一定由无线容量不足导致？” |
| 住宅区掉线 | 异常释放、无线链路、切换和告警之间的并列假设 | “为什么降低释放触发频率不等于业务改善？” |
| 枢纽间歇退服 | 告警、可用率与恢复事件；先对齐时间再推断 | “告警与退服同窗还缺什么因果证据？” |

## 数据与工具契约

`wireless_demo` 提供 catalog、read_case、prepare_memory、compare_candidates、select_candidate、reveal_feedback、learn、memory，可由 Harness 按任务选择。`wireless_data_analyze` 可用于合成和真实观测，接受 JSON 数组或 JSONL 文件，也接受内联 observations；每次最多 10,000 条 / 8 MB。

数值观测至少保留 `object_id`、`time_window`、`kind`、`metric`、`value`、`unit`、`definition`、`source_ref`；人群不同用 `cohort` 区分，样本量用 `sample_count`，阈值需同时提供 operator、value 和 source_ref。时间要求带时区。分析结果按对象、指标、定义、单位、人群分组，隔离冲突记录；均值只对等长不重叠窗口计算，百分率均值不冒充合并计数器结果。

已有工单可以用 `wireless_workorder export_trace` 导出执行事实，需传当前 `execution_id`。若要给长期 Pass/Fail，还需明确 `long_eval_result`、`long_eval_source_ref` 和 `evaluation_visible_at`；普通前后差异不会自动授予长期标签。要进入源策略效果统计，实际下发状态也须有来源保留；工具不会仅凭执行成功补写下发成功。合成 Trace 不能以 historical 模式编译。

场景库经验包保存在 `WIRELESS_DATA_DIR/demo-sandbox/<数据版本>/` 下，普通生产检索不扫描这个空间；即使直接读取 demo 包，普通候选工具仍保留来源隔离，不用于现场决策。场景服务只在显式 sandbox 内允许调用相同源消费者，所有结果携带合成范围标签。

## 安装、生成与检查

```bash
python3.12 -m venv backend/.runtime/wireless-python
backend/.runtime/wireless-python/bin/pip install -r backend/dsh/dsh-wireless/compiler-requirements.txt

cd backend
npm run demo:build
npm run test:wireless-demo
npm run test:harness

cd ../frontend
npm run build
```

数据生成器与种子固定，重新生成会更新数据清单和场景卡。测试实际调用编译器、源 ranker 和源值选择器，验证六类记忆、八类场景、反证、参数缺口、厂家隔离、反馈前不可揭示、正/反效果学习、版本保留、幂等与 SDK 工具注册。编译结果与工单账本属于忽略的运行时数据；不要把它们当真实现场工单提交。
